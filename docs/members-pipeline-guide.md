# 주소록 자동 갱신 파이프라인 — 운영자 가이드

> ⚠️ **폐기(2026-07-14): 주소록은 Supabase 실시간 DB로 이관됨.** 이 구글시트→GitHub Actions→`members.enc`
> 파이프라인은 더 이상 사용하지 않습니다(워크플로 삭제됨). 운영은 **`docs/members-supabase-guide.md`** 를
> 따르세요. `build-members-enc.mjs`/`encrypt-members.mjs`는 비상 복구용으로만 남겨 둡니다. 아래 내용은 사료입니다.

> **(구) 이 문서가 최신입니다.** `docs/members-public-sheet.md`(공개용 주소록 파생 시트 안내)와
> 내용이 상충하면 이 문서를 따르세요. 그 문서는 "구글 시트를 공개 CSV로 게시"하는 구식 방식을
> 설명하고 있고, 이 파이프라인은 시트를 **비공개로 유지한 채** 서비스 계정으로 읽어 `members.enc`
> (암호문)만 커밋하는 방식입니다. 시트를 웹에 게시할 필요가 없습니다.

## 개요

매일 새벽 3시(KST), GitHub Actions가 비공개 구글 시트 2개(① 주소록 원본, ② 동문 근황·연락처
설문 응답)를 구글 서비스 계정으로 읽어 병합한 뒤, 접속 코드로 암호화해 `data/members.enc`에
커밋합니다. 시트나 회원 개인정보는 어떤 시점에도 공개 URL이나 로그에 노출되지 않습니다.

수동으로 즉시 실행하고 싶으면 GitHub 저장소 → **Actions** 탭 → **update-members** →
**Run workflow** 버튼을 누르면 됩니다.

## ① 구글 서비스 계정 만들기

1. [Google Cloud Console](https://console.cloud.google.com/)에서 새 프로젝트를 만듭니다.
   (개인 Gmail 계정으로 가능하며, 조직 계정이나 결제 정보가 필요하지 않습니다.)
2. 좌측 메뉴 → **API 및 서비스 → 라이브러리**에서 **Google Sheets API**를 검색해 **사용 설정**합니다.
3. **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → 서비스 계정**을 선택합니다.
   - 이름은 자유롭게(예: `mr40-members-bot`).
   - 역할(권한) 부여 단계는 **건너뛰어도 됩니다** — 이 서비스 계정은 프로젝트 안에서 아무 GCP
     리소스도 다루지 않고, 오직 사람이 초대해 준 구글 시트만 읽습니다.
4. 생성된 서비스 계정을 열어 **키 → 키 추가 → 새 키 만들기 → JSON**을 선택해 JSON 키 파일을
   다운로드합니다. 이 파일 안에 `client_email`과 `private_key` 필드가 있습니다.
   **이 JSON 파일은 다른 곳에 올리지 말고, 아래 ③번에서 시크릿 등록 후 즉시 삭제하세요.**

## ② 구글 시트 2개를 서비스 계정에 공유하기

- **주소록 원본 스프레드시트**와 **연락처 설문 응답 스프레드시트**를 각각 엽니다.
- **공유** 버튼 → 위 JSON 키 파일의 `client_email` 값(예:
  `mr40-members-bot@프로젝트ID.iam.gserviceaccount.com`)을 입력 → 권한은 **"뷰어"**로 충분합니다.
- 시트를 "웹에 게시"할 필요는 없습니다 (오히려 비공개로 두어야 안전합니다).

## ③ GitHub Secrets / Variables 등록

저장소 **Settings → Secrets and variables → Actions**에서 등록합니다.

### Secrets (Secrets 탭)

| 이름 | 값 |
|---|---|
| `GSA_CLIENT_EMAIL` | JSON 키의 `client_email` 값 |
| `GSA_PRIVATE_KEY` | JSON 키의 `private_key` 값 (`-----BEGIN PRIVATE KEY-----`로 시작하는 전문 그대로) |
| `MEMBERS_CODE` | 주소록 접속 코드 (동문에게 공지하는 코드와 동일해야 함) |

> **왜 `client_email`과 `private_key`를 각각 시크릿으로 나누어 등록하나요?**
> JSON 키 파일 전체를 시크릿 하나로 통짜 저장하면, 워크플로 로그의 GitHub 자동 마스킹이
> JSON 안에 있는 개별 값(이메일, 키)을 정확히 못 찾아내는 경우가 있어 실수로 로그에 일부가
> 노출될 위험이 커집니다. 필드별로 나눠 등록하면 각 값이 독립적으로, 확실하게 마스킹됩니다.

`private_key`를 붙여넣을 때 줄바꿈이 그대로 유지돼도 되고, 한 줄로 합쳐 `\n`이 리터럴
문자로 들어가도 됩니다 — 스크립트가 둘 다 처리합니다.

### Variables (Variables 탭)

| 이름 | 값 | 기본값(비워도 되는지) |
|---|---|---|
| `MEMBERS_SHEET_ID` | 주소록 원본 스프레드시트 ID (URL의 `/d/`와 `/edit` 사이 문자열) | 필수 |
| `RESPONSES_SHEET_ID` | 연락처 설문 응답 스프레드시트 ID | 비워두면 응답 병합 없이 원본만 사용(경고 로그 1줄) |
| `MEMBERS_SHEET_RANGE` | 주소록 탭 이름과 범위 | 기본값 `주소록!A:H` |
| `RESPONSES_SHEET_RANGE` | 응답 탭 이름과 범위 | 기본값 `설문지 응답 시트1!A:L` |

## ④ 첫 구동 확인

1. GitHub 저장소 → **Actions** 탭 → 왼쪽에서 **update-members** 워크플로 선택.
2. **Run workflow** 버튼으로 수동 실행.
3. 실행 로그에서 `changed (회원 N명)` 또는 `no-change`가 출력되는지 확인합니다.
   (회원 이름·연락처 등 실제 데이터는 로그에 절대 출력되지 않습니다.)
4. `changed`였다면 저장소에 `chore(members): 주소록 자동 갱신` 커밋이 새로 생겼는지 확인합니다.

## 데이터 계약 (참고)

- **주소록 원본 탭**(A:H, 1행 헤더): 이름, 기수, 소속, 이메일, 전화번호, 관심사, 한마디, 회장 —
  사이트가 그대로 쓰는 스키마입니다.
- **응답 시트**(A:L, 1행 헤더): A 타임스탬프, B 기수, C 이름, D 휴대폰, E 이메일, F 주소·근황,
  G 공개 범위, H 개인정보 동의, I 최종학력, J 전공, K 현재 소속·직위, L 경력.
- 병합 규칙(요약): H가 "동의"로 시작하는 응답만 유효 → 같은 사람(이름+기수)의 최신 응답이
  최종 → 원본에 있으면 전화번호/이메일/소속/한마디 갱신(빈 값이면 기존 유지), 없으면 새 회원
  추가 → G가 "비공개"를 포함하면 원본에 있어도 최종 출력에서 제외 → 기수 오름차순, 같은 기수
  내 이름 가나다순 정렬. 상세 구현은 `scripts/build-members-enc.mjs`의 `mergeMembers()`를
  참고하세요.

## 운영 주의사항

- **서비스 계정 키 로테이션**: 90일 주기로 새 JSON 키를 발급해 `GSA_CLIENT_EMAIL`/
  `GSA_PRIVATE_KEY` 시크릿을 갱신하고, GCP 콘솔에서 이전 키는 삭제하는 것을 권장합니다.
- **공개 저장소의 스케줄 자동 비활성화**: `kaistmr/mr40-website`는 공개 저장소이므로, 저장소에
  **60일간 커밋이 없으면** GitHub가 `schedule` 트리거를 자동으로 비활성화합니다. 이 경우 매일
  갱신이 조용히 멈추므로, Actions 탭에서 `update-members` 워크플로가 "This scheduled workflow
  is disabled" 상태인지 가끔 확인하세요. 재활성화는 워크플로 페이지 우측의 **"Enable workflow"**
  버튼 한 번으로 됩니다.
- **접속 코드 변경 시**: 동문 공지용 접속 코드를 바꾸면 `MEMBERS_CODE` 시크릿도 반드시 함께
  갱신하세요. 시크릿만 바꾸고 다음 실행 때 시트 내용이 조금이라도 바뀌어 있으면(또는 강제로
  `workflow_dispatch`를 실행하면) 새 코드로 다시 암호화되어 커밋됩니다. 시트 내용이 우연히
  전혀 안 바뀐 상태에서 코드만 바꾸면 스크립트가 기존 파일을 새 코드로 복호화하지 못해 "변경
  있음"으로 판단하고 새 코드로 재암호화하므로, 이 경우도 정상 동작합니다.
